ASSISTED ENTRY — TRIAL
=======================

A second, semi-automatic way into the app. The manual results page is untouched
and remains the primary path; this sits beside it on a new "Assisted entry" tab.


HOW IT WORKS

  1. Press "Read latest from play.nla.gd".
  2. Each game's latest result is read and lined up against what the app holds.
  3. Every row gets a status:

       NEW        not in the app — a draw number is suggested and it can be
                  accepted
       MATCHES    already entered and identical — nothing to do
       CONFLICT   the app and the site disagree — shown in red, and it CANNOT
                  be accepted from this page
       PUBLISHED  already sent — a difference is a correction, not an entry
       OTHER DAY  belongs to a different date than the one on screen

  4. For a NEW row, confirm the draw number, optionally add the payout, press
     Accept.
  5. Accepting SAVES the result as an ordinary entry. It does not send and does
     not publish. Open the results page, finish it, and send as usual.


WHAT THE PAGE CAN AND CANNOT GIVE

  supplies  winning numbers, Multi-X, the draw's date and time, jackpots
  does NOT  draw numbers, payouts, prize tiers, or any history

DRAW NUMBERS are therefore SUGGESTED from the app's own sequence — the last
stored number for that game plus one — and shown alongside "last was 830" so
the operator can see what it is based on. They are editable. Nothing is taken
from the page, because the page does not carry them.

PAYOUTS are still entered by hand, here or on the results page.


CONFLICTS MUST BE RESOLVED BY A PERSON

If the app says 3X and the site says 5X, one of them is wrong. The page says so
plainly and offers no Accept button. Fix it on the results page, then re-read.
There is no bulk accept, deliberately: a scrape that silently overwrote an
operator's entry would be worse than no scrape at all.

A PUBLISHED RESULT IS NEVER OVERWRITTEN. The accept endpoint refuses it:
  "That draw has already been published. Correct it on the results page and
   resend."


WHY IT PARSES TEXT, NOT MARKUP

play.nla.gd is generated by the Abrazo web sales platform and its markup can
change without notice. Matching on tag structure would break silently. The
parser works on the visible text and the game logo filenames, and reports what
it could not find rather than returning a half-empty result.

TESTED against two real captures of the live page taken hours apart, before and
after the evening draws landed. All six games parsed correctly both times, with
periods mapped from the draw times, digits kept in draw order, letters and
jackpots extracted, and no problems reported.


A REAL FINDING FROM BUILDING THIS

play.nla.gd currently shows LOTTO $152,000 and SUPER 6 $587,000. The figures
pushed to the websites were 148,000 and 507,000 — an $80,000 gap on Super 6.
Worth checking what the public sites show right now. This is exactly the drift
the tool is meant to catch.


FILES
  netlify/functions/lib/playScrape.mjs   the parser
  netlify/functions/auto-entry.mjs       read + reconcile (writes nothing)
  netlify/functions/accept-scraped.mjs   saves one reviewed result
  src/views/AutoEntryView.jsx            the review page
  src/lib/api.js                         two new calls
  src/App.jsx                            the new tab
  src/styles.css                         styling

DEPLOY
  git add -A
  git commit -m "Assisted entry: read results from play.nla.gd for review"
  git push

No database change. No new environment variables.


WORTH KNOWING BEFORE YOU RELY ON IT

  - Only the LATEST result per game is on that page. A draw missed while the
    next one is already showing cannot be recovered from it — the manual path
    is still needed for anything older.
  - The page has no draw numbers, so the sequence assumption (last + 1) is the
    app's, not the site's. After a cancelled or moved draw, check it.
  - This does not replace the Abrazo data feed requested from CBN. That has the
    draw numbers, payouts and prize tiers this page lacks.
