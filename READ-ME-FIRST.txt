FIX: a single-draw send went out as the complete day's results
===============================================================

WHAT WENT WRONG
When the sender was rebuilt for throttling, the trigger stopped passing the
operator's selection - it sent only the draw date. The sender then rebuilt the
email server-side with kind='eod' HARDCODED, so every send became the full
end-of-day results regardless of what was selected. This also silently broke
the RESENT banner.

THE FIX
The browser already builds the exact email it shows in the preview. That message
is now stored on the run and sent unchanged. The server never rebuilds it, so
what you preview is what sends - one draw, a whole day, or a resend.


HOW TO APPLY  (four steps)
==========================

1. SQL  -  run supabase/07_blast_run_message.sql in the Supabase SQL editor.
   (Adds subject / html / text_body / scope_label / scope_kind / is_resend
   to blast_runs. You may already have done this.)

2. FUNCTIONS  -  copy these two files into the app repo, overwriting:
        netlify/functions/send-blast.mjs
        netlify/functions/send-blast-slice.mjs

3. CLIENT  -  copy apply-fix.mjs into the ROOT of the app repo (the folder with
   package.json) and run it:

        node apply-fix.mjs

   It edits src/lib/api.js and src/views/ResultsView.jsx in place, replacing
   sendBlast() and confirmSend() and adding markResent() if missing. A .bak of
   each file is written first. It is safe to run twice - it detects work already
   done and skips.

   You can then delete apply-fix.mjs; it is a one-off tool, not part of the app.

4. BUILD AND PUSH

        npm run build
        git add -A
        git commit -m "Send the previewed email, not a rebuilt end-of-day document"
        git push

   If the build fails, restore and tell me what it said:
        mv src/lib/api.js.bak src/lib/api.js
        mv src/views/ResultsView.jsx.bak src/views/ResultsView.jsx


VERIFY AFTER DEPLOY
===================
Select ONE draw (e.g. Afternoon Pop). Check the preview shows only that draw,
then send to one address you control.

   select scope_kind, scope_label, is_resend, subject is not null as has_message
   from blast_runs order by started_at desc limit 3;

has_message should be true and scope_label should name the draw you chose.

If it still says "The email could not be prepared", the client patch has not
taken effect - check that step 3 ran without errors and that the build deployed.
